# PodDump v0.4.0

수집 제한 시간이 끝나도 이미 읽은 메모리와 CPU 기록을 유효한 부분 Core로 남깁니다. 읽지 못한 범위와 시도하지 못한 범위를 구분하고, 정지한 스레드를 해제한 뒤 저장과 확인값 계산을 마칩니다. 파일이 다른 것으로 바뀌었거나 임시 파일을 지우지 못했을 때도 그 실패를 기록합니다.

Pod의 프로세스 식별 정보를 읽지 못한 경우를 프로세스가 없는 경우와 구분합니다. 동시에 파일 연결을 이어받은 실행이 있어도, 정상 수집이 끝난 자원은 즉시 반환하도록 공유 자원 잠금을 보강했습니다. 같은 Pod의 중복 요청 조정과 다른 시점의 재수집은 계속 구분합니다.

실제 Kubernetes에서 기본 수집, 41개 스레드, 큰 메모리, 닫힌 메모리 파일의 매핑, 제한 시간 만료를 확인했습니다. 버퍼 사용·직접 쓰기 두 방식의 제한 시간 6조건에서 부분 Core 12건과 실행 재개를 대조했습니다. AL2023 6.1.189·6.12.113·6.18.56 및 Ubuntu AWS 6.8.0-1067에서는 별도 파일 목록을 가진 스레드까지 포함해 Core의 CPU 기록을 대조했습니다. Ubuntu AWS 7.0.0-1014에서는 실제 Pod를 사용했습니다.

72개 자동 검사와 공유 자원 반환 관련 전체 검사 100회 반복을 통과했습니다. 의존 파일은 배포된 확인값과 대조했고 RustSec 검사에서 알려진 취약점이나 경고가 검출되지 않았습니다. 커널별 시험은 해당 빌드의 검증이며 모든 설정·보안 정책에서의 수집 가능성을 뜻하지 않습니다. 여러 프로세스의 Core와 커널 덤프는 서로 다른 순서와 시각에 수집됩니다.
